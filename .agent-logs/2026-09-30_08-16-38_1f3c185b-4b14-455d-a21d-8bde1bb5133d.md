# Fathom clone: scope and build plan

## 1. Critique

Your direction is mostly right. The upload pipeline stands in for the bot, seeded real meetings mean the demo never waits on an API, and a single Next.js app is enough. I'd change six things:

1. **Make upload P0, not P1.** The whole scope rests on the claim that "upload replaces the bot." If that path doesn't work live, reviewers are looking at a viewer of pre-baked data, and they will try uploading a file. Write the pipeline once as a shared library that both the seed script and the upload route call. The upload UI then costs about 2 hours.
2. **Share the whole meeting in P0, not only clips.** Fathom's core loop is "the recap reaches everyone who attended." A read-only `/share/m/[token]` page is cheap and shows that loop. Clips can stay P1.
3. **Link every AI output to a timestamp.** Summary bullets, action items, decisions, chapters and Q&A citations should all seek the player when clicked. This is Fathom's signature feel, and it's what makes the AI output checkable. Treat it as P0.
4. **Add speaker naming.** Diarization returns "Speaker A–H", which looks unfinished. Have the LLM guess names from the transcript ("thanks, Priya") and add a rename UI, plus merge-speakers for when diarization splits one person in two. You need this for an 8-person call.
5. **Chapters and talk-time are nearly free.** Chapters come out of the same LLM pass and talk-time is plain arithmetic over segments. "Ask this meeting" needs no RAG: an hour of transcript is about 15–20k tokens, so it fits in context. Do all three of your P1.5 items instead of picking 2–3.
6. **Cut the "Upcoming meetings" calendar stub.** Fake UI costs credibility. Also cut team-only sharing, which needs real auth. Use "anyone with the link" plus revoke.

Missing pieces that matter for judging:
- A **README** covering the architecture, why each item was cut, and how a real bot would plug in (Recall.ai or a Meet/Zoom SDK → the same pipeline).
- A **processing-status UI**: uploading → transcribing → analyzing → ready/failed.
- **Abuse limits on public upload**, since every upload costs money: cap size and length, and require a demo passcode.
- A short demo video.
- Your agent logs, committed at the end as planned.

## 3. Data model (Postgres, Drizzle)

```
users            id, name, email, avatar_url            -- one seeded demo user
user_settings    user_id PK, default_template, auto_action_items bool,
                 bot_name, auto_share bool

meetings         id, owner_id, title, started_at, duration_ms,
                 media_url, media_kind (video|audio), poster_url,
                 status (uploaded|transcribing|analyzing|ready|failed), error,
                 source (seed|upload), asr_job_id,
                 attribution_text, attribution_url, created_at

participants     id, meeting_id, speaker_label ('A'), display_name,
                 color, talk_ms, segment_count, is_name_guessed bool

transcript_segments
                 id, meeting_id, participant_id, idx, start_ms, end_ms,
                 text, words jsonb [{w,s,e}], tsv tsvector GENERATED
                 idx: (meeting_id, start_ms), GIN(tsv)

summaries        id, meeting_id, template, status (pending|ready|failed),
                 content jsonb {sections:[{heading, bullets:[{text, seg_ids[]}]}]},
                 markdown, model, created_at        UNIQUE(meeting_id, template)

action_items     id, meeting_id, text, owner_participant_id NULL, owner_text,
                 due_text ('by Friday'), due_date NULL, segment_id, start_ms,
                 done bool, source (ai|manual)

insights         id, meeting_id, kind (decision|key_point|open_question),
                 text, segment_id, start_ms

chapters         id, meeting_id, idx, title, summary, start_ms, end_ms

highlights       id, meeting_id, title, note, start_ms, end_ms, created_by, created_at

share_links      id, token (random 22 chars), resource_type (meeting|highlight),
                 resource_id, revoked_at, view_count, created_at

qa_messages      id, meeting_id, question, answer, citations jsonb [{seg_id,start_ms}]
```

Design choices:
- Action items, insights and chapters don't depend on the template. They're generated once. Only `summaries` varies by template.
- Templates (General, Sales, Customer Success, Demo, Q&A, Retrospective) are prompt configs in code, not database rows.
- The LLM refers to **segment IDs**, never raw timestamps. The server validates each ID and maps it to `start_ms`. This removes hallucinated timestamps.

## 4. Seed data

Aim for 6–8 meetings, fewer and better rather than many and thin.

| Slot | Source | License |
|---|---|---|
| **Long meeting (~60 min, 8+ speakers, video)** | A public Zoom recording such as a GitLab team meeting or a Kubernetes SIG/community meeting on YouTube, found with YouTube's Creative Commons filter | Must show "Creative Commons Attribution license" on the video page. ⚠️ Not all GitLab/CNCF videos are CC. Check each one. |
| **4 audio-only meetings** | AMI Corpus: the ES2002a–d series (the same 4-person design team across 4 meetings, which shows recurring participants nicely) | CC BY 4.0, attribution required |
| **1–2 short ones (5–15 min)** | Another CC-BY Zoom clip, or one you record yourself | Recording your own gives full control, and it becomes your live upload test file |

**Download**
- AMI: groups.inf.ed.ac.uk/ami/download. Select the meetings and pick the "Headset mix" audio.
- YouTube: `yt-dlp -f "bv*[height<=720]+ba" --merge-output-format mp4 <url>`. Downloading is a YouTube ToS grey area even for CC content. Say so in the README and credit the source on the meeting page.
- Timebox picking the long meeting to 30 minutes. The first thing to check is audio quality: each person on their own mic, little crosstalk.

**Process** with `scripts/seed.ts`, which is idempotent:
1. Transcode with ffmpeg: `-vf scale=-2:540 -c:v libx264 -crf 28 -c:a aac -b:a 96k -movflags +faststart`. Faststart is required for instant seeking. Also extract a poster frame and a 16 kHz mono MP3 for speech recognition.
2. Upload the media to R2.
3. Transcribe with AssemblyAI (`speaker_labels`, `speakers_expected`) and **save the raw JSON to `seed/fixtures/`** in git.
4. Run the LLM analysis and all templates, and save that output to fixtures too.
5. Load the database from fixtures. Re-seeding then never calls a paid API again.

Use AssemblyAI over Deepgram: it takes speaker-count hints and diarizes well on large calls. Both cost pennies per hour.

## 5. Routes and meeting-page UX

```
/                       → redirect /meetings
/meetings               list, upload button, status chips, search box
/meetings/[id]?t=123    meeting page
/search?q=              global results → /meetings/[id]?t=
/highlights             my clips
/settings
/share/m/[token]        public read-only meeting (no edit controls)
/share/clip/[token]     public clip
API: /api/uploads/sign · /api/meetings · /api/meetings/[id]/process
     /api/webhooks/assemblyai · /api/meetings/[id]/summaries/[template]
     /api/meetings/[id]/ask   (+ server actions for small mutations)
```

**Meeting page for an hour-long, 8-person call** (desktop, two columns):
- **Header:** title, date, duration, a stack of 8 avatars (click for talk-time bars and rename), Share, and "Copy link at current time".
- **Left column (about 60%):**
  - Player, with a custom scrubber showing chapter segments (hover shows the title) and optionally thin per-speaker activity lanes.
  - Tabs underneath: **Summary** (template dropdown, copy) · **Action items** · **Decisions** · **Chapters** · **Highlights** · **Ask**.
- **Right column (full height): transcript.**
  - Search box with match n/m and Enter to step through.
  - Speaker filter chips.
  - The current segment is highlighted and held about ⅓ from the top. Scrolling manually pauses auto-follow and shows a "↓ Jump to current" pill.
  - Long monologues are split into paragraphs of 30 seconds or less.
  - Selecting text shows "Create clip".
- **One `seekTo(ms)`:** every timestamp in the app calls it, and it seeks, plays and scrolls the transcript.
- **Keyboard:** space, ←/→ 5s, `/` for search, speed 1–2×.
- **Mobile:** sticky player on top, with Transcript as one more tab.

## 7. Top risks

| Risk | De-risk |
|---|---|
| **Diarization on 8 speakers** | Choose clean Zoom audio; pass `speakers_expected`; rename/merge UI as the fallback; check the long meeting first, in hour 2, so there's time to swap sources |
| **Large media** | Supabase free tier caps files at 50 MB and Vercel request bodies at 4.5 MB, so use **R2 with presigned direct upload** (free egress). Transcode seeds to 540p with faststart (~200 MB/hr). Don't transcode user uploads; play them as-is. |
| **Serverless timeouts** | Transcription is webhook-driven. Run the LLM analysis in the webhook route with `maxDuration` 300, as parallel calls (analysis ‖ default summary). Other templates generate on demand and are cached. |
| **Player sync jank** | Use `requestAnimationFrame` while playing, binary search over segments, re-render only when the active segment changes, no virtualization (about 1,500 rows is fine). Faststart makes seeking instant. |
| **Hallucinated timestamps or owners** | Refer to segment IDs only, validate server-side and drop invalid ones; owners must match a participant or stay as plain text |
| **API cost and abuse** | Fixtures mean seeds cost once. Cap uploads (≤200 MB, ≤90 min), require a demo passcode, set spend limits on both API keys. |
| **Licensing** | CC-BY sources only, attribution shown on each meeting page and in the README |
| **Running out of time** | A hard P0 line at hour 12; nothing after it is load-bearing |

**Stack:** Next.js App Router, TypeScript, Tailwind, shadcn/ui on Vercel. Neon Postgres with Drizzle. Cloudflare R2 for media. AssemblyAI for transcription. Claude Sonnet 5 with structured output for summaries and analysis. No separate backend.
