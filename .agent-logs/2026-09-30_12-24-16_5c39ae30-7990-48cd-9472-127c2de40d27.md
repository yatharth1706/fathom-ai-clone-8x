The upload flow (hours 10–12) is built and committed as `317dec0`, so all the P0 features are in. Typecheck and lint pass, and a 3-minute test clip went all the way through to a finished meeting in about 30 seconds.

**How it works:**
- **Upload:** "Upload recording" on My meetings opens a drag/drop dialog. The browser checks type, size (100 MB) and length (15 min) before sending anything, then uploads straight to R2 with a progress bar.
- **Server checks:** `/api/uploads/sign` repeats the size and type checks and enforces 3 uploads per IP per day (`UPLOAD_DAILY_LIMIT`). It creates the meeting and returns a signed upload URL locked to the exact file size.
- **Transcription:** `/api/meetings/[id]/process` confirms the file arrived and sends it to AssemblyAI. The webhook (`/api/webhooks/assemblyai`) and the status endpoint's polling both use the same step, so a transcript is only processed once. The 15-minute limit is checked again against AssemblyAI's measured length.
- **Notes:** after transcription, the AI names speakers, writes a title, chapters, action items and decisions, then generates the default summary. If the AI step fails, the meeting still opens with its transcript and a warning banner.
- **Status:** while it's processing, the meeting page shows a progress stepper (or the error). Both the stepper and the list check for updates every 3 seconds.
- **Cleanup:** uploads never finished after 30 minutes are marked failed. Meetings stuck in "Generate notes" for 20 minutes are released with their transcript.

One change from the plan: the summary runs after speaker naming instead of in parallel. In parallel, the first test's summary said "Speaker A" while the transcript showed "Azalea". If the naming step takes over 30 seconds, the summary is skipped so everything fits the 300-second limit, and the Summary tab offers a Generate button.

**What I tested:**
- Rejection of bad input, wrong file types, and files over 100 MB or 15 minutes.
- The fourth upload from one IP in a day is refused.
- An upload with the wrong size is rejected by R2.
- Processing the same meeting twice is refused, and a missing file marks the meeting failed.
- A run driven only by simulated webhook calls: a wrong secret is rejected, repeated calls processed once, no duplicate rows.
